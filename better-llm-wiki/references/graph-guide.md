# Graph Guide — the `.graph` protocol

The wiki's graph protocol is a derived file layer, not a second source of truth.

- Humans and agents edit `wiki/**/*.md`.
- `scripts/lint_wiki.py` validates those files and compiles graph artifacts.
- Frontends read `.graph` files for fast global and local graph views.

This keeps Markdown authoritative while making graph loading fast.

## Design goals

- **Single truth**: page content and links live only in Markdown.
- **Fast local graph**: opening one page should not require loading the full graph.
- **Fast global graph**: the full graph should be loadable from a small number of precompiled files.
- **Incremental lint**: only changed pages and affected neighbors are recompiled.
- **Stable IDs**: every page node is identified by its wiki-root-relative path, e.g. `wiki/concepts/Tool Calling.md`.
- **Separated concerns**: graph semantics and graph layout are stored separately.

## Directory layout

```text
<wiki-root>/
├── wiki/
│   ├── concepts/
│   ├── entities/
│   └── summaries/
├── graph/
│   ├── manifest.graph
│   ├── nodes.graph
│   ├── adjacency.graph
│   ├── edges-000.graph
│   ├── recent.graph
│   ├── navigation.graph
│   ├── lineage.graph
│   ├── settings.graph
│   ├── stats.graph
│   ├── issues.graph
│   └── view.graph
└── .graph-cache/
    ├── page-hashes.graph
    ├── reverse-links.graph
    └── dirty.graph
```

Additionally, each wiki page may have a local sidecar cache:

```text
wiki/concepts/Tool Calling.md
wiki/concepts/Tool Calling.md.graph
```

## File responsibilities

### Per-page sidecar — `wiki/**/*.md.graph`

Local graph cache for one page. This is the fastest path for "open current page and show its local graph".

```json
{
  "schema": 1,
  "id": "wiki/concepts/Tool Calling.md",
  "title": "Tool Calling",
  "displayName": "Tool Calling",
  "shortName": "Tool Calling",
  "qualifiedName": "concepts / Tool Calling",
  "breadcrumb": ["wiki", "concepts", "Tool Calling"],
  "fileName": "Tool Calling.md",
  "parentName": "concepts",
  "kind": "concept",
  "hash": "sha256:...",
  "tags": ["agents", "tools", "orchestration"],
  "summary": "Agent deciding when and how to invoke tools.",
  "ego": {
    "out": [
      {"to": "wiki/concepts/Tracing.md", "kind": "links_to"},
      {"to": "wiki/entities/OpenAI Agents SDK.md", "kind": "links_to"}
    ],
    "in": [
      {"from": "wiki/index.md", "kind": "links_to"}
    ]
  },
  "stats": {
    "inbound": 1,
    "outbound": 2,
    "degree": 3
  }
}
```

Rules:

- Generated by `lint`; never edit by hand.
- Must be deleted when the backing `.md` file is deleted or renamed.
- Contains enough information to render a one-hop local graph without touching global files.

### `graph/manifest.graph`

Top-level manifest for readers.

```json
{
  "schema": 1,
  "generatedAt": "2026-04-27T16:00:00+08:00",
  "root": "demo-wiki",
  "nodesFile": "nodes.graph",
  "adjacencyFile": "adjacency.graph",
  "edgeShards": ["edges-000.graph"],
  "recentFile": "recent.graph",
  "navigationFile": "navigation.graph",
  "lineageFile": "lineage.graph",
  "settingsFile": "settings.graph",
  "statsFile": "stats.graph",
  "issuesFile": "issues.graph",
  "viewFile": "view.graph"
}
```

### `graph/nodes.graph`

Global node catalog.

```json
[
  {
    "id": "wiki/concepts/Tool Calling.md",
    "title": "Tool Calling",
    "displayName": "Tool Calling",
    "shortName": "Tool Calling",
    "qualifiedName": "concepts / Tool Calling",
    "breadcrumb": ["wiki", "concepts", "Tool Calling"],
    "kind": "concept",
    "tags": ["agents", "tools"],
    "summary": "Agent deciding when and how to invoke tools.",
    "degree": 3
  }
]
```

Display-name rules:

- `id` is the stable unique key and always remains a wiki-root-relative path.
- `title` comes from frontmatter `title`, then H1, then the file stem.
- `displayName` is the default graph label.
- `shortName` is the compact label for dense graph views.
- `qualifiedName` is for search results and sidebars where duplicate names need context.
- `breadcrumb` is for navigation and hover details.
- For `index.md`, the fallback display name is the parent folder name, so folder-split pages do not all render as `index`.

### `graph/adjacency.graph`

Global neighbor lookup for fast local expansion.

```json
{
  "wiki/concepts/Tool Calling.md": {
    "out": [
      {"to": "wiki/concepts/Tracing.md", "kind": "links_to"},
      {"to": "wiki/entities/OpenAI Agents SDK.md", "kind": "links_to"}
    ],
    "in": [
      {"from": "wiki/index.md", "kind": "links_to"}
    ]
  }
}
```

### `graph/edges-*.graph`

Global edge shards for full-graph rendering.

```json
[
  {
    "s": "wiki/concepts/Tool Calling.md",
    "t": "wiki/concepts/Tracing.md",
    "k": "links_to",
    "w": 1,
    "d": 1
  }
]
```

### `graph/recent.graph`

Recent activity graph compiled from log entries within the last 21 days.

The graph uses two synthetic time-bucket nodes:

- `recent`: pages touched within 0-7 days.
- `lastweek`: pages touched within 7-14 days.

Pages touched 14-21 days ago are retained as floating page nodes with no synthetic edge. This keeps older context visible without making the recent graph feel falsely connected.

```json
{
  "schema": 1,
  "window": {
    "kind": "relative_day_buckets",
    "anchorDate": "2026-05-15",
    "ranges": {
      "recent": { "fromDaysAgo": 0, "toDaysAgo": 7, "node": "recent" },
      "lastweek": { "fromDaysAgo": 7, "toDaysAgo": 14, "node": "lastweek" },
      "floating": { "fromDaysAgo": 14, "toDaysAgo": 21, "node": null }
    },
    "historyDays": 21,
    "datesByBucket": {
      "recent": [],
      "lastweek": [],
      "floating": ["2026-04-27"]
    },
    "availableLogDays": 1,
    "includedLogDays": 1,
    "entryLimit": null,
    "touchedNodeLimit": null
  },
  "entries": [
    {
      "id": "log-entry:20260427-1428-ingest-structmem",
      "date": "2026-04-27",
      "time": "14:28",
      "op": "ingest",
      "title": "structmem-long-horizon-behavior-llms",
      "logPath": "log/20260427.md",
      "anchor": "1428-ingest-structmem",
      "ageDays": 18,
      "bucket": "floating",
      "touched": [
        "wiki/summaries/structmem-long-horizon-behavior-llms.md"
      ],
      "nodes": [
        {
          "id": "wiki/summaries/structmem-long-horizon-behavior-llms.md",
          "displayName": "structmem-long-horizon-behavior-llms",
          "qualifiedName": "summaries / structmem-long-horizon-behavior-llms",
          "kind": "summary"
        }
      ]
    }
  ],
  "nodes": [
    {
      "id": "recent",
      "kind": "recent",
      "displayName": "Recent 7 days",
      "qualifiedName": "Recent activity / 0-7 days",
      "entries": [],
      "d": 1
    },
    {
      "id": "lastweek",
      "kind": "recent",
      "displayName": "Last week",
      "qualifiedName": "Recent activity / 7-14 days",
      "entries": [],
      "d": 0.58
    },
    {
      "id": "wiki/summaries/structmem-long-horizon-behavior-llms.md",
      "kind": "summary",
      "displayName": "structmem-long-horizon-behavior-llms",
      "qualifiedName": "summaries / structmem-long-horizon-behavior-llms",
      "bucket": "floating",
      "buckets": ["floating"],
      "entries": [
        {
          "id": "log-entry:20260427-1428-ingest-structmem",
          "date": "2026-04-27",
          "time": "14:28",
          "op": "ingest",
          "title": "structmem-long-horizon-behavior-llms",
          "logPath": "log/20260427.md",
          "anchor": "1428-ingest-structmem",
          "ageDays": 18,
          "bucket": "floating",
          "d": 0.26
        }
      ],
      "d": 0.26
    }
  ],
  "edges": []
}
```

Rules:

- Generated by `lint`; never edit by hand.
- Reads `log/YYYYMMDD.md` entries as the primary activity source.
- Recovers commits that changed `wiki/` without changing a log file from git history when the wiki root is also the git repository root. Properly logged commits are skipped by this fallback, so operations are not duplicated.
- Uses standard Markdown links and backticked `wiki/...md` literals in log bodies to find touched pages.
- Keeps all entries from log files whose dates fall within the last 21 days.
- Does not cap touched page nodes. If the included log days touched many pages, `recent.graph` should include them all.
- Uses synthetic `recent` and `lastweek` nodes. Do not create log-file or log-entry nodes in `nodes`.
- Edges use `k: "touched"` from `recent` or `lastweek` to page nodes. If multiple entries touch the same page in the same bucket, merge them into one edge, increment `w`, keep the entry records in `edge.entries`, and set edge `d` to the newest/strongest entry depth for that bucket/page pair.
- Pages in the 14-21 day bucket are floating nodes: include them in `nodes`, but do not create a `floating` synthetic node or touched edge.
- Per-entry id, title, op, time, log path, anchor, age, and bucket live in top-level `entries[]`, synthetic node `entries`, page node `entries`, and `edge.entries`; they are metadata, not graph endpoints.
- Never put `log/YYYYMMDD.md#entry-heading` fragments into `s`, `t`, or node ids. Graph endpoints must remain stable ids that do not break file-path indexes.
- Each edge carries a `d` (depth) field: `1.0` = newest date, decreasing as entries age. Viewers use `d` to render edge color from dark (recent) to light (old).
- All non-recent edges default to `d: 1`.

### `graph/navigation.graph`

Navigation graph compiled from `wiki/index.md`.

```json
{
  "schema": 1,
  "root": "wiki/index.md",
  "nodes": [
    {
      "id": "nav:wiki/index.md",
      "kind": "index",
      "displayName": "Index",
      "page": "wiki/index.md"
    },
    {
      "id": "nav:wiki/index.md#concepts",
      "kind": "section",
      "displayName": "Concepts",
      "level": 2,
      "page": "wiki/index.md"
    },
    {
      "id": "wiki/concepts/Tool Calling.md",
      "kind": "concept",
      "displayName": "Tool Calling",
      "qualifiedName": "concepts / Tool Calling"
    }
  ],
  "edges": [
    {"s": "nav:wiki/index.md", "t": "nav:wiki/index.md#concepts", "k": "contains", "w": 1, "d": 1},
    {"s": "nav:wiki/index.md#concepts", "t": "wiki/concepts/Tool Calling.md", "k": "listed_in", "w": 1, "d": 1}
  ]
}
```

Rules:

- Generated by `lint`; never edit by hand.
- Treats `wiki/index.md` headings as section nodes.
- Treats Markdown links inside index sections as page nodes.
- Uses `contains` for index-to-section edges and `listed_in` for section-to-page edges.

### `graph/lineage.graph`

Lineage graph for the "raw sources -> wiki pages -> concepts/entities" story.

```json
{
  "schema": 1,
  "nodes": [
    {
      "id": "raw/papers/example.md",
      "kind": "raw_source",
      "displayName": "Example Paper"
    },
    {
      "id": "wiki/summaries/example.md",
      "kind": "summary",
      "displayName": "Example summary"
    },
    {
      "id": "wiki/concepts/Tool Calling.md",
      "kind": "concept",
      "displayName": "Tool Calling"
    }
  ],
  "edges": [
    {"s": "raw/papers/example.md", "t": "wiki/summaries/example.md", "k": "ingested_as", "w": 1, "d": 1},
    {"s": "wiki/summaries/example.md", "t": "wiki/concepts/Tool Calling.md", "k": "mentions", "w": 1, "d": 1}
  ]
}
```

Rules:

- Generated by `lint`; never edit by hand.
- Adds raw-source nodes from files under `raw/`.
- Uses page frontmatter `sources` for `raw/... -> wiki/...` `ingested_as` edges.
- Uses summary page links for `summary -> target` `mentions` edges.
- Uses non-summary page `sources` values pointing at wiki pages for `derived_from` edges.

### `graph/settings.graph`

Viewer hints and lightweight graph semantics. This file is derived and safe for frontends to read before choosing a layout.

```json
{
  "schema": 1,
  "hiddenKinds": ["query"],
  "defaultView": "knowledge",
  "views": ["knowledge", "recent", "navigation", "lineage"],
  "layout": {
    "knowledge": {"engine": "forceatlas2"},
    "recent": {"engine": "bipartite"},
    "navigation": {"engine": "tree"},
    "lineage": {"engine": "dag"}
  },
  "typeAffinity": {
    "entity": {"concept": 1.2},
    "source": {"source": 0.5}
  }
}
```

Rules:

- Generated by `lint`; never edit by hand.
- Keep it advisory. Readers may ignore any setting they do not support.
- Do not put user viewport state here; use `view.graph` for that.

### `graph/stats.graph`

Global counts and aggregates.

```json
{
  "pages": 8,
  "edges": 14,
  "orphans": 0,
  "deadLinks": 0,
  "byKind": {
    "concept": 4,
    "entity": 2,
    "summary": 2
  }
}
```

### `graph/issues.graph`

Machine-readable lint findings relevant to graph display.

```json
{
  "orphans": [],
  "deadLinks": [],
  "missingIndexEntries": []
}
```

### `graph/view.graph`

Optional persisted layout and viewport state.

```json
{
  "positions": {
    "wiki/concepts/Tool Calling.md": {"x": 120, "y": 80}
  },
  "zoom": 0.9,
  "pan": {"x": 0, "y": 0}
}
```

Rules:

- `view.graph` is not rewritten by `lint`.
- Frontends may own this file.
- Semantic graph data and user layout state must stay separate.

### `.graph-cache/*`

Implementation detail for incremental compilation.

- `page-hashes.graph`: content hash per Markdown page.
- `reverse-links.graph`: reverse inbound index for invalidation.
- `dirty.graph`: optional snapshot of pages marked dirty in the current run.

These files may be regenerated freely and do not need to be user-facing.

## Recommended edge semantics

For knowledge-base display, keep semantics light:

- `links_to`
- `mentions`
- `summarizes`
- `derived_from`
- `ingested_as`
- `contains`
- `listed_in`
- `touched`
- `related_to`
- `contradicts`

Start with `links_to` only if needed. Add other edge kinds only when the extractor is reliable.

## Incremental lint behavior

`lint` has two deliberately different graph paths:

1. Incremental lint detects changed pages from git/stat state, re-extracts their metadata and links, and rewrites only their page-local sidecars.
2. Incremental lint always refreshes `recent.graph`. It loads the compiled node catalog, then reads only explicitly touched pages that are missing from that catalog, so a newly ingested page appears without a whole-corpus scan.
3. Full lint scans `wiki/**/*.md`, computes hashes, repairs affected neighbors, and rebuilds `nodes.graph`, `adjacency.graph`, edge shards, `navigation.graph`, `lineage.graph`, `settings.graph`, `stats.graph`, and `issues.graph` in addition to `recent.graph`.
4. All graph outputs use atomic writes. Timestamp-only changes do not rewrite semantically unchanged artifacts.

## Rename and delete handling

Renames and deletes need explicit cleanup:

- Remove the stale `*.md.graph` sidecar for the old path.
- Remove the old node ID from global files.
- Remove or update inbound and outbound references in cache files.
- Recompute orphan and degree stats for affected neighbors.

## What not to do

- Do not hand-edit `.graph` files.
- Do not store graph layout in `nodes.graph` or `edges-*.graph`.
- Do not treat `.graph` files as source material for wiki writing.
- Do not introduce a second link syntax inside Markdown just for graph extraction.

Markdown links remain the source; `.graph` files are compiled artifacts.
